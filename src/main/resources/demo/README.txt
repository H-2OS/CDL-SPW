================================================

cover-demo.jpg
--------------
用途：取色窗口里那块「示例歌词」预览条渲染**封面**时使用。

用户要求（原话）：「封面，**随包自带**。**在任意机器上都显示这个封面内容**。」
—— 即它必须是**随包资源**，不依赖任何本机文件/音乐库。

来源与加工（如实记录）
----------------------
- 源文件：用户提供 `C:\Users\31866\Desktop\封面.jpg`（**6000×6000，3015113 B**）
- 加工：**面积平均（box filter）**等比缩放到 **1024×1024**、JPEG 质量 0.92
  → **171735 B（约 168 KB）**
- 加工工具：一次性 Java 程序（`AssetDiag.java` / `CoverDiag2.java` / `MakeLow.java`，
  放在 `%TEMP%\coverdiag\`），跑完即弃，**不是**构建步骤的一部分。
- 因此本目录里的文件是**派生副本**，不是原始文件。

### ⚠️ 2026-09-22 重制（第二版）—— 为什么不是 512

第一版是 **512×512**（= 部署包里那个 **51,007 B** 的文件）。
**实测它本身带混叠**（一次性程序 `AssetDiag`，与 6000 原图面积平均直出的"理想 512"对比）：

| | 理想 512（6000 面积平均直出） | 部署包里的 512 | 比值 |
|---|---|---|---|
| 梯度能量（512 原生） | 4.5781 | **6.3653** | **1.3904×** |
| 与理想 512 的平均绝对像素差 | — | 2.67 / 255 | — |
| 再各自面积平均降到 105px | 9.0427 | 9.1794 | 1.015× |

⇒ 第一版素材在**原生分辨率**下就带 **+39% 的假高频**（= 混叠，典型成因是"单步"降采样：
只采 2×2 = 4 个源像素，而 11.7× 下采样理想应采 11.7² ≈ 137 个）。

⚠️ **但素材不是主因** —— 上表最后一行说明：只要**全程走面积平均**，
那点残留混叠到 105px 时只剩 **+1.5%**。用户看到的"糊"是**缩放路径**造成的（见下）。

用户原话：「示例封面很**糊**，不清晰，影响观感，**我提供给你的原文件都没这么糊**。」

### ⚠️⚠️ 2026-09-22 第二次修正：上面那张表**复现不出来，已作废**

第一版 README 给过一张"512 / 1024 / 2048 的梯度能量比值表"（512 = 0.971×、1024 = 0.989×…）。
**那张表用现有文件复现不出来**，而且它把"糊"的**归因搞反了**。
实测（一次性程序 `CoverDiag2`，目标 105px，理想基准 = 6000 原图面积平均直出 = **31.2605**）：

| 素材 | 最近邻 | 双线性 | 双三次 | 面积平均 |
|---|---|---|---|---|
| 512（**部署包里那一版**，51,007 B） | 39.4091 (**1.261×**) | 37.1282 (1.188×) | 38.5424 (**1.233×**) | 31.3367 (1.002×) |
| 1024（本版，171,735 B） | 38.2496 (1.224×) | 37.5321 (1.201×) | 38.0699 (1.218×) | 31.2438 (**0.999×**) |

⇒ 三条**推翻第一版 README** 的结论：

1. **"糊"的主因是缩放路径，不是素材分辨率。** 同一张 512 素材：单步双三次 **1.233×**
   （+23% 假高频 = 混叠），面积平均 **1.002×** —— 差 **23%**。
2. **素材 512 → 1024 只贡献约 0.3%**（同一条面积平均路径下 1.002× vs 0.999×）。
3. **梯度能量在这里不是"越锐越好"**：512 素材在双线性下是 1.188×，比 1024 的 1.201×
   还"低" —— 那**不是更清晰**，只是混叠成分不同。本表的正确读法是"**离 1.000× 越近越好**"。

（第一版 README 说"512 = 0.971×（**低于**基准 = 过平滑）"，实测是 **1.002×**，**不是过平滑**；
而且部署包里那个 512 是 **51,007 B**，与第一版 README 记的"44 KB"**不是同一个文件**。
两处都对不上，故整段作废。**上面第一版那段"1.20×"的措辞同样以本表为准。**）

### 结论：1024 够不够？—— **够**，而且判据不在"梯度能量"

- 素材 1024 ÷ 真机最大显示边长 105px = **9.75×**；② 的黑胶几何让封面**内容**再缩到 2/3
  ⇒ 70px，即 **14.6×**。
- 在**面积平均**路径下，1024 素材缩到 105px 已达 **0.999×**（与 6000 原图直出无差别）。
- 探针里的**素材分辨率下限**断言取 `边长 ≥ 最大显示边长(105) × 3 = 315`
  （见 `CoverScalerProbe` §3）。1024 的余量是 **3.25×**。

⚠️ **光换素材不会让用户看到的封面变清楚** —— 还必须**重新部署**，让真机也走
`CoverScaler`。实测部署包里那个 `IslandWindow.class` **不引用 `CoverScaler`**
（`grep -ac CoverScaler` = 0），即真机仍在做单步双三次下采样（上表 1.233× 那一列）。
（渲染目标尺寸：预览 `side = 76px`；真机 `cover.scale_with_font = false` 时上限 56px、
 默认 `true` 时 = 歌词区高度 − 20，默认字号下约 105px。）
